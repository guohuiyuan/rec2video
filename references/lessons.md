# 录屏剪辑的经验与坑

## 一、剪辑顺序：先配音，再剪画面

这是唯一正确的顺序，反了必返工。

| 做法 | 结果 |
|---|---|
| 先按经验剪 82.5s → 再配音 78.66s | `stretch = 0.9535`，画面快 4.6%，到第 11 段画面比旁白早 **2 秒**，文案与画面对不上 |
| 先配音 77.54s → 按每段旁白长度反剪 | `stretch = 1.0000`，13 个推镜严格落在预设段首偏移上，全程不漂 |

原因很简单：旁白长度由 TTS 决定，不可控；画面取材长度完全可控。所以让可控的去适配不可控的。

`cut` 已经强制这个顺序（没 `timeline.json` 直接退出），`--preview` 也只按完整旁白算 stretch，不按截断时长算。

## 二、坐标：人看原片，渲染吃画框

最容易翻车的地方，这次返工两遍。

- 原片 2560×1440 crop 之后缩进 1560×878 的画框，比例 `1560/2560 = 878/1440 ≈ 0.6094`。
- 第一版锚点拍脑袋填画框坐标，整体**偏下 100–180px**：讲「点一下扩散一圈」时画面停在面板下方的空白处，讲 Click Effects 时停在了别的控件上。
- 第二版手算 0.609 对了，但麻烦。现在 `zooms` 直接吃**原片像素坐标**，自动减 crop 偏移再换算：

```
frame_x = (src_x - crop_x) * frame_w / crop_w
```

实测三条与手工调好的值逐一对上（780,400 → 780,402；150,200 → 150,234；1064,190 → 1065,194）。

另外：**anchor 一定要取 `plan.src` 的尺寸**。`cut` 之后 `project.video.src` 已经是裁好的 2560×1440，再按它减一次 crop 偏移就把偏移算了两遍（脚本里已处理，但改代码时别改回去）。

## 三、取材点：联系表是唯一可靠依据

这次 6 分钟录屏里，**前 60 秒全是 OBS + 浏览器准备素材**，Recordly 从 69 秒才出现。净可用素材 290 秒，最后用了 12 段共 77 秒。

具体错过的点：

- 第一版 s01 取 62s，抓到了下载弹窗 → 后移到 69.8s。
- 第五段（讲鼠标）取 101s，那时左侧还是**背景面板**，光标面板 105.5s 才展开 → 后移 4.5s。
- 第九段（讲导出）原本是右侧被挤压的小面板 → 换到 157.5s 那张完整导出面板。

结论：`at` 填完必须回联系表盯一眼那 6 秒，别信记忆。

## 四、ffmpeg 硬坑

| 症状 | 原因 / 修法 |
|---|---|
| `x264 [error]: malloc failed` | 2560×1440 crf16 会吃满内存 → 加 `-threads 2` |
| `Output file does not contain any stream`（拼接时） | concat demuxer 不认 Windows 绝对路径的冒号 → list.txt 写相对文件名 + `cwd=切片目录` |
| 画面上残留浏览器标签栏/任务栏 | crop 的 y 太靠上；实测这个项目是 `2560:1440:0:60`（标题栏 60px，任务栏在 1600-1440=160 之外刚好切掉） |
| 联系表时间戳全是 `0s` 起 | `-ss` 之后 `pts` 归零 → 标签用 `%{eif\:trunc(t+起点)\:d}s` |
| 联系表中文标签乱码/报错 | drawtext 缺字体 → 显式 `fontfile='C\:/Windows/Fonts/msyh.ttc'`（盘符冒号要转义） |

## 五、画框与字幕的几何关系

1920×1080 输出、画框 1560×878、上边距 56 → 下沿 934，只剩 146px。

- 两行字幕（46px 字号 + 行距）约 94px，所以**字幕必然贴着画框下方**，`margin_v` 只能给到 46 左右（越小越靠下）。
- 想要明显留白，只能压 `frame.h`（并同步把 crop 高度调小），调 `margin_v` 是调不出来的。
- `check` 在底部余量 < 130px 时会提醒。

## 六、文案与画面的三种错位

1. **情绪错位**：画面已是套好背景的漂亮界面，旁白说「一看屏幕：干巴巴」。钩子句要描述观众此刻**真的看到**的东西。
2. **指代错位**：旁白「点一下就套上」，画面却在拖滑杆。一段只配一个动作。
3. **数字错位**：口播说「三十个书源」，UI 显示「22 个渠道」，封面又写 22。发布前把标题/封面/简介/口播里的名词数字对一遍。

## 七、非软件录屏的取材差异

- **教程 / 讲课录屏**：往往自带讲解旁白，可以保留原声，只补字幕和推镜；这时 `segments` 用原声切段（`voice.provider = files`），`cut` 的段长改从原声字幕的时间轴算。
- **手机竖屏录屏**：crop 出 9:16 后画框要改（如 540×960），不要硬塞进 16:9 —— 两侧会是大片背景。竖版成片更适合直接用 `cover.py` + `assets/templates/hero.html` 出竖版封面。
- **游戏 / 动画类录屏**：画面本身在动，推镜要么不用、要么只做缓慢的 Ken Burns（倍率 1.05–1.1），高频推镜会晕。
- **产品演示（带鼠标点击）**：推镜 + 点击音效收益最大，锚点就压在鼠标落点上。

## 八、配乐这条链的三个坑

1. **下载单曲必须带 `source`。** `music-dl` 的 `/music/download` 是 `id` + `source` 双参数，缺一个直接 `400 Missing params`；搜索能出结果不代表能下。`bgm.py` 现在从搜索结果里把 `source` 带过去，手工下也要记得加：`get <id> <out> --source netease`。
2. **`MUSIC_BASE` 要指到 `…/music`。** `music-dl web -p 8080` 的服务根路径是 `/music`，少这一段会拿到 404 的 HTML。
3. **不要假设用户先起了服务。** 没服务时脚本会下官方 release 的可执行文件、起一个只听 `127.0.0.1` 的临时实例，用完关掉——但它要下 ~13 MB，走代理可能只有十几 KB/s，所以要并发分片 + 整轮重试。离线场景用 `--no-local` 直说不行，别在那儿干等。
4. **PATH 上那个 `music-dl` 可能不是同一代。** 老版本（如 v1.3.1 TUI 版）`web` 只有 `-p`，硬塞 `--no-browser` 直接 `unknown flag` 起不来；就算起来了，页面挂在 `/`、没有 `/music/api/*`，探测 `/music/` 会一直 404。现在的做法：先问一次 `web --help` 决定要不要加 `--no-browser`；起不来回退到官方 release（缓存里有就直接用，别重下 13 MB）。手工排障就一条命令看它到底认不认：`music-dl web --help`。

## 九、改文案是「重配 + 重切 + 重渲」，不是只重渲

改一句文案会同时动两样东西：**旁白时长**、**每段画面该多长**。原来两处缓存都只看「文件在不在」，于是静默复用旧产物：

| 缓存 | 症状 | 现在的做法 |
|---|---|---|
| `vo/segNN.mp3` | 文案换了，`tts` 照样打印「复用 10 段配音」，声音还是旧的，字幕和画面对不上 | `vo/manifest.json` 记文案+音色的 sha1，指纹不符就重配，并打印「文案变了 → 重新配音」 |
| `work/cuts/sNN.mp4` | `cut` 报告「画面 58s」，实际拼进去的还是 62s 的旧切片，`check` 报 `stretch 0.94` | 切片名带参数指纹 `s01_<md5(at|want|crop|fps)>.mp4`，参数一变自然重切，旧切片顺手清掉 |

所以改文案的标准动作就三条，不要省：

```bash
python scripts/rec2video.py script demo/project.json narration.txt   # 灌文案
python scripts/rec2video.py tts    demo/project.json                 # 指纹变了会自动重配
python scripts/rec2video.py cut    demo/project.json                 # 按时长重切（不放心就 --force）
python scripts/rec2video.py build  demo/project.json
```

两个附加事实：

- **同一段文案两次 TTS 时长可能差 3–4 秒**（语速有随机性）。所以别手动把 `max` 卡死在旧时长上，留 0.5–1.0s 余量；`cut` 会按新的 `dur + gap` 重新算。
- `build` 只会在 `plan.json` 齐全**且** `video.src` 还不指向 `screen-edit.mp4` 时自动 cut。已经 cut 过一遍的工程，改完文案必须手动跑 `cut`，否则 `build` 用旧画面配新旁白。

## 十、开场素材：先确认前几秒是「稳的」

用户录屏时经常先拖窗口、缩放页面，开头 0–5 秒画面尺寸在变。这种段直接当第一段，成片第一帧就是「页面偏小、四周一片背景」，三秒内就掉人。

做法：抽原片 `1–10s` 逐秒帧（`fps=1/1.0:start_time=1`），找出**页面尺寸不再变化**的那一秒，`at` 从这里起。本次实测原片 0–5s 窗口在缩放，5.2s 之后才稳。

但别为了稳定把第一段推到和后面重复的位置——三段画面一模一样，观众会以为卡了。稳定点和「画面有推进」之间要取平衡：宁可第一段短一点（5s 左右），也不要 7 秒都停在同一屏。

## 十一、标题改了，封面和简介不会自己跟着改

标题、封面大字、口播首句、简介首句是同一个东西的四种说法（`SKILL.md` 3.4）。**没有任何命令会把它们串起来重算**，改标题时四处都得手动过一遍：

| 产物 | 怎么改 |
|---|---|
| 封面大字 | 改 `cover/spec.json` 的 `title_cn` / `desc`，再 `cover.py render cover/spec.json -o cover -s 16x9,4x3` |
| 口播第一段 | 改 `narration.txt` 第一行 → `script` → `tts`（指纹变了自动重配）→ `cut` → `build` |
| 简介首句 | 手写，按标题同义复述 |

两个坑：

- **别用 `rec2video.py cover` 改文案**。它会重抓仓库信息、**整个覆盖 `spec.json`**，手写的 `title_cn` 直接没了。重出封面只该用 `cover.py render <已有的 spec.json>`。
- **`cover.py` 依赖 playwright**，WorkBuddy 托管的 python 通常没装。用装了的那一个跑（本机是 `C:\Users\guohuiyuan\miniconda3\python.exe`），否则会静默只出 `spec.json`。

## 十二、标题不落盘 = 没有标题

前几版把「先定标题、第一句复述标题」写在 SKILL 里，实际交付还是翻车：标题只活在对话里，`project.json` 没有字段装它，于是没有任何东西能验首句——写顺了是运气，写歪了也没人拦。

修法是把标题变成工程数据：

- `project.json` 加 `title`（发布标题原文）。`new --title` / `script --title` 都能写。
- `scripts/hookcheck.py` 拿 `title` 和 `segments[0]` 比四件事：标题在不在、项目名、数字、3-gram 字面重合。
- `script`、`check` 自动跑，另外单开 `hook` 子命令（✗ 时退出码 2）。
- 比对前先挖掉 `[笑]` 气声标记和 `好家伙/神器/狠活/斩获/Github/Stars` 这类套话——复述允许丢套话，不该因此判不及格。

> 1.3.3 起这条判据整体换掉了：四条改五条、LCS ≥ 85%、套话不再挖（第十八节）。留在这里是为了记住"复述"这个词曾经怎么把人带偏。

实测：anything-analyzer 那条片标题写了「斩获 3.9k Stars」，首句只有「抓包、MITM、指纹伪装…神器」，数字一个都没落——这种漏，肉眼对着两段文字看三遍也未必发现，机器一秒就报出来。

**教训**：凡是"规则"都该有个字段装它、有个命令验它。只写进文档的规则，下一次一定漏。

## 十三、music-dl 不能"有就用"，得认版本

`ensure()` 原来先 `shutil.which()`，于是本机 PATH 上的 `music-dl.exe`（v1.3.1，老 TUI 构建）永远优先——版本号还比 release 的 `v1.1.7` 大，怎么比都是"更新"。

实际状况是两条产品线：老的 TUI 版把 web 页面挂在 `/`，没有 `/music/api/*`；新 release 才有 `/music/` 那套接口。光看"进程起来了"发现不了，取 BGM 时才 404。

- 判据改成**版本号等于 release 的 `tag_name`**，不是"谁大用谁"。
- 缓存的官方二进制排在 PATH 前面（`find_bin()` 顺序：`MUSIC_DL_BIN` > 缓存 > PATH）。
- `installed.json` 记下装的是哪个 tag，免得每次跑都去 `--version` 问一遍。
- `release.json` 缓存 latest 信息 6 小时，代理挂了不至于每次卡在网络超时上。
- 想钉死某份：`MUSIC_DL_BIN`（会提示版本不符）；想将就：`--any`。

## 十四、四处重复借的是广告手法，语气跟不上就成了祥林嫂

3.4 的四点对齐一开始只被当成"一致性检查"——标题、封面、首句、简介口径别打架。真发出去才看清它的另一面：**同一句话在四个入口被说四遍**，这就是广告的做法，不是说明书的做法。

手法借了广告，语气就必须跟上。同样四个入口，如果全是平铺直叙的白描句，观众的观感不是"这项目真猛"，而是"这人怎么老说这一句"——重复把平淡放大了四倍，反而比只说一遍更尴尬。

第一条容易走偏的地方是**把手法当身份**：写成"这条片子是广告"，语气就跟着滑向卖货，介绍片该有的"这东西真能干活"的可信度就没了。正确说法是借广告的钩子打法，片子本身仍然是项目介绍，看完要人去拉仓库，不是下单。

拆开是三样东西，缺一样都塌：

| 要素 | 提供什么 | 缺了会怎样 |
|---|---|---|
| 重复（四处） | 频次 → 熟悉感 | 说一次就没影，观众记不住 |
| 浮夸（情绪词、短句节奏） | 记忆点 → 点得进去 | 祥林嫂，平淡的话说四遍 |
| 具体（数字、功能、体积） | 可信度 → 留下来 | 吹牛不打草稿，第一反应是营销号 |

落点：3.1 开头先讲清"借的是广告手法，不是把片子做成广告"；`hook.md` 〇节给出三件套和「浮夸 / 造假」对照表；第 7 节写明标题是第一声也是最响的一声；白描体那一段补了"白描 + 四处重复是最难受的组合，不适配就走两处"。

两条剂量线（都是实测踩出来的）：

1. **重复止于四个入口**。第 2 段往后再说「神器」「狠活」，就从广告变成复读机，第 5 秒就走人。
2. **浮夸只加在形容词和节奏上**。数字、功能、star 数一个都不许动——「14 个源，狠活」可以，「全网通吃」不行。越界的代价不是被骂，是被截图挂出来。

**教训**：定了一条"四处说同一句话"的规则，就得同时定这句话该用什么语气说。只规定重复、不规定情绪，等于规定了复读。

## 十五、躲一个难看的数字，把整句的承重墙一起拆了

同一个坑，一次踩出两个洞。

新项目 star 只有两位数，`斩获 XX.Xk Stars` 写不出来。当时的处理是"那这段不写了"——把狠活体的后半截整个删掉，标题缩成「狠活！「novel-scan」，一本 txt 换 26 个文件」。发出去才发现问题：**star 数没写，GitHub 也没了**。信息流里「GitHub 又出狠活」这五个字承担的是"这是真项目、有代码可拉"的默认信任，删掉它省下的不是一行字，是观众点进来的理由。

根子在把标题看成一整块，删就一起删。其实狠活体是三段结构，松紧完全不同：

```
[平台前缀：GitHub 又出狠活]  +  [硬数字]  +  [能力清单]
        承重（删了没人信）        可替换        承重（删了不知道干啥）
```

`斩获 XX.Xk Stars` 只是数字槽里的一个候选，槽还在，换个真数字填进去就行——产物数、耗时、代码量，哪个都比两位数的 star 有说服力。正确写法是「GitHub 又出狠活！一本 .txt 换 26 个文件：书评、人物卡、人物图」，一样没有 star，但三段都在。

第二个洞在同一句里：**「26 个产物」是从界面截图抄的**。录屏上白纸黑字写着「查看所有产物 (26)」，直接搬进文案，念出来却是一团模糊——观众不知道产物是书评、图片还是日志。系统用词（产物 / 结果 / 内容 / 数据）是给开发者看的字段名，卖点必须是观众能想象出形状的东西：书评、人物卡、人物图、JSON。

**教训**：删任何一个元素前，先问它是承重墙还是装饰。「不许编数字」≠「不许提数字」，解法是换数字；「口播不念 GitHub」≠「标题不写 GitHub」，前者是省 1.5 秒，后者是丢全部信任。界面上的文案只负责说明状态，不负责卖东西——照抄之前先翻译成观众的语言。

## 十六、把"情绪"和"气声"混成一条规矩，结果把质感一起限死了

novel-scan 那支 47 秒的片，9 段口播只有头尾两个 `[笑]`，中间 7 段干干净净。按当时的规矩没有错——3.1 写着"情绪只放头和尾"，3.3 写着"气声放句首，别每段都加"。但听完的第一反应是：**在念稿**。

问题在于这两条被写成了同一条。**文案的情绪强度**确实该只放头尾（全程甲亢等于没有甲亢），**气声是听感颗粒度**，性质完全不同：它是"这个人说话时在笑"，不是"这句话很激动"。用一条"别每段都加"同时管住两者，等于规定了这个声音只能有一个表情。

落点：把两层的规矩拆开——3.1 的"情绪只放头尾"只管文案口径，3.3 单独管气声。剂量最后落到**开头一个**：第 1 段句首固定 `[笑]`，收尾求和 Star 那句可以再来一个，中间不加。

剂量是试出来的，不是拍的。第一版写成"每句挂一个"，9 句全挂之后旁白从 47 秒涨到 54.2 秒，多出来的 7.1 秒里 6 秒是笑——笑本身好听，但一句一个的密度把整片节奏切成一小段一小段，反而听不清在讲什么。开头那一声值钱，是因为它唯一；每句都笑，它就不值钱了。

顺带踩出两个技术坑：

1. **标签不等于声音，时长更是完全靠不住**。这一版先把 `[笑]` 判成"生效"，依据就是带标签的比不带的长 0.5–1.5 秒——结果拉开包络一看，多出来的那段是 **0 电平静音**：`voice-120`（大肥鱼）把 `[笑]` `[轻笑]` `[咯咯笑]` `[清嗓]` 全渲染成 1 秒空白，只有 `[冷笑]` 出了声。所以"时长变长"不是笑声的证据，静音占位也会变长；判据只能是包络（那段有没有能量）或耳朵。**别把没验听的"开头有笑"写进交付说明**——这次就是这么发出去的，观众第一句听到的是一秒空白。
2. **气声塞在句中时，方括号后多写一个空格**，`script` 的 `re.sub` 只删方括号，字幕里会留一个空格，跟着烧进画面。句中写法必须是 `skill，[轻笑]扫完`，不能是 `skill，[轻笑] 扫完`。

真笑的两条可行路：换到会笑的音色（`voice-114` 铃兰、`voice-162` 能天使有非语音发声），或把笑写成念出来的「哈哈」「嘿嘿」——是词不是标签，一定有声。

**教训**：一个声音能承载的表情有层次——语气强弱、气声频率、语速松紧是三根不同的旋钮，别用一条规则一起拧。定规矩时先问"我在管哪一层"，管错了层，规则越严格执行起来越死板。

## 十七、简介写完就交，回头才发现少了标签

Wechatsync 那支片交付时，简介只给了两行正文——首句复述 + 干货。看着挺完整，发布时才发现**没有话题标签**：平台只能拿标题去猜这条该推给谁，等于自己把流量入口关了一半。补标签这一步落在发布前几分钟，最容易漏；漏了不报错，也不影响成片，所以没人会记得。

问题出在规矩只写到颗粒度的一半：3.4 里只规定了「简介首句」的字数口径，**整段简介的结构从来没写**。写了一半的规格，执行时就会交付一半的东西。落点是把简介补成完整的交付形态——三行（首句 / 干货 / 标签），标签 5–8 个、`#GitHub` 必带、只用空格分隔（见 `SKILL.md` 3.5），并写进第 6 节自检。

顺带两条判断：标签是**申请流量池**，不是装饰——少于 3 个等于没申请，堆到十几个就变成营销号特征；`#一篇文章同步29个平台` 这种自造长句没人搜，占着名额还显得外行。另外公众号正文里的 `#` 不是话题，同一段简介投过去要删掉标签行、改在「话题」里加。

**教训**：一个交付物只要被拆成「必须项 + 可选项」，可选项就永远不做。简介的规格必须覆盖到它被发布时的样子，而不是覆盖到「我们常说出口的那部分」。

## 十八、「第一句复述标题」写进规矩两个版本，用户还是纠了两次

第一次是 novel-scan：标题为了躲一个难看 star 数，把「GitHub 又出狠活」整句砍了，首句也跟着"精简"。第二次是花笺：标题 44 字，首句 34 字，读着顺、也说清了是什么，但「GitHub」「Markdown 双栏实时预览」「斩获」全没了，与标题的字面重合只有 33%。用户的评价只有一句：「skill 下次记得用标题来当第一句话啊」。

两次都不是执行者偷懒，是**规矩本身留了缝**。旧规矩写的是「把标题翻译成口语当第一段」，机检只要求 3-gram 重合 ≥ 20%，而且比对前会把「好家伙 / 神器 / 狠活 / 斩获 / Github / Stars」这些套话先挖掉——**等于告诉执行者：压字数是对的，丢套话是允许的**。一条规则只要允许"稍微顺一点"，每个环节都会顺手顺一下，最后剩下的是一句更好读、但和标题无关的话。

落到具体，这些词恰好都是承重的：`GitHub` 是信息流的信任锚（观众看到它才默认有代码可拉）；「Markdown 双栏实时预览」是仓库里最硬的一条能力；「斩获 5.6k Stars」是唯一的社会证明。压掉它们，标题买来的注意力在视频第一秒就退了货。

改法不是"下次更认真"，是把缝关掉：

1. 规则从「复述」改成**「照念」**——第 1 段就是标题原句，一字不改，句首只加一个 `[笑]`。
2. 判据从 3-gram 20% 改成 **LCS 覆盖率 ≥ 85%**，而且**套话不再挖掉**；标题里每个数字必须全落（照念不可能漏，漏了就是改写版）。
3. 只留三条例外：`[笑]` 标记；TTS 一定念错的词（**改标题，不改首句**）；标题 > 40 字时砍最前面的套话句头（给 `!`，不算 ✗）。
4. 连带把**标题长度上限从 60 字降到 40 字**（念完约 8 秒），"前三秒给什么"从"第一句怎么排"前移到"标题怎么排"——既然口播是照念，语序完全由标题决定。
5. 第一段的素材要求跟着变：要撑 8–10 秒的连续动作，不再是过去 5 秒。

代价是真实的：标题不能随手写长句了，写长了自己念不完。好处也真实——**标题和口播不再是两份东西，做不出"标题党 + 正文另一套"**，写标题时就得按"念出来听"来写。

**教训**：规矩里每一条"可以稍微……"的余地，都会被用来省力。要的是重复，就别写"复述"；要的是原句，就写"照念"，并且把判据的阈值抬到只有原句能过。改措辞比加提醒有用——提醒会被忘记，阈值不会。

## 十九、只播「跑起来了」却没亮出最终成品，观众看完等于白看

做 `sprite2video` 介绍片时，原始录屏停在 Agent 刚拆出六步清单、还在抓仓库数据的 `Running...` 状态，后面真正渲染出来的动画视频没有录进去。结果整条介绍片把仓库、命令、任务清单讲得清清楚楚，最后却没让观众亲眼看到它生成的成品长什么样。

观众点进一条工具/生成器/Agent 介绍片，耐心撑到结尾只为了看一件事：**「你吹了半天，跑出来的东西到底长啥样？」** 只给过程不给成品，就像厨师录了 60 秒切菜下锅，最后锅盖还没掀开就喊「觉得有用点个 Star」——转化率直接腰斩。

硬规矩落成三条：

1. **看联系表时先找「最终成品」**：`scan/sheet_*.jpg` 里必须第一时间标出成品出现的秒数（生成图、成片播放、导出结果、跑起来的页面），在 `plan.json` 里为它单独预留 4–8 秒清晰特写段，绝不能为了凑时长把它裁掉。
2. **原录屏没录到成品，先补再剪**：如果录屏停在生成中 / 进度条上，剪辑前先向用户要最终成品文件（成片视频、生成图或结果截图），或者从目标仓库/本地产物里取真实样片，拼在收尾段展示（视频片段可直接按同样 `crop`/`fps` 接进 `screen-edit.mp4`，静态成品图可叠加 `cards` 或转成带轻推镜的展示片段）。
3. **开头可预告，结尾必验收**：像 `female-portrait-director` 那样用最终成图当第 1 段「结果先行」很吸睛，但结尾仍要亮出完整成品做闭环——观众记住的是最后一眼看到的成片质感，不是半路的加载条。

**教训**：演示工具可以省略中间 200 秒的等待，唯独不能省略最后 5 秒的成品。没有成品画面的介绍片，本质上只是口头说明书。
